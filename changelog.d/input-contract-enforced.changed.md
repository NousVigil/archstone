- **BEHAVIOUR CHANGE: a capability's declared `input:` is now enforced before the provider is called.** Until now `inputSchema` was advertised but never checked, so arguments of the wrong shape (an object where a `location` string is declared, a free-text date, a negative `party` count, an undeclared key) were forwarded to the backend, and only the backend's own validation stopped them. `callTool` (MCP, stdio and HTTP) and `execute()` (embedded) now validate the arguments with one shared `validateInput` in `@archstone/emitter-support`, after the lifecycle and policy gates and before rate limiting and any connector work. A mismatch returns `isError: true` with `_meta["dev.archstone/input_invalid"]` (`{ error, capability, problems: [{ path, expected }], truncated? }`, at most 16 problems), or `ExecuteResult.denial = { reason: "input_invalid", capability, problems }`, and the audit record is `phase: "denied"`, `denialReason: "input_invalid"`. The refusal names declared field paths and fixed expectations only; it never contains a value or an undeclared key name the caller sent. Nothing is coerced: a wrong type, a missing required field, a value outside an `enum`, a malformed `date`/`date-range`/`date-time`, a non-integer or negative `party` count, a malformed `money`, and **any undeclared key (top level, or inside `money`, `party`, `date-range`)** are all refused; `null` on an optional field still counts as absent. The advertised `inputSchema` is now closed to match (`additionalProperties: false` at every object level, `minimum: 0` on `party` counts), so a client that sent extra keys, numbers for strings or free-text dates and was accepted before will now be refused. `execution.schema.json`'s `denialReason` enum gains `input_invalid`.
